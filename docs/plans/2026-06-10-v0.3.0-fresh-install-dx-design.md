# v0.3.0 Fresh-Install and Design-System Integration Design

## Problem

Installing the table into a real project does not produce a finished, usable
data table. It looks acceptable in the playground, but much of that appearance
comes from playground-only styles. In a fresh Vue/Vite project the table is
mostly unstyled — no header background or spacing, no row structure — and the
first row is incorrectly highlighted blue before any interaction. Pagination
exists internally but renders no controls. The package does not integrate
naturally with Tailwind/shadcn projects: AI tools often pick the unstyled
entry and generate generic controls that ignore the application's existing
shadcn components. The documentation does not give developers or AI a
reliable installation path, and some examples describe props and events the
component does not support.

Version 0.2.6 passes its unit tests and builds successfully, but the package does
not deliver the experience promised by its documentation when installed into a
new Vue/Vite application.

The audit reproduced the following failures from the packed npm artifact:

1. Importing `@ioi-dev/vue-table` does not add package CSS to the consumer
   bundle. The generated library entry no longer contains the source CSS import.
2. Explicitly importing `@ioi-dev/vue-table/styles.css` still produces a mostly
   unstyled table. The polished default theme exists only in playground CSS.
3. The first row receives the blue focused-row background on initial render
   because keyboard state starts at row index `0`, even while document focus is
   on `<body>`.
4. Pagination slices rows but renders no pagination UI. Consumers cannot see the
   page count or navigate without writing their own controls.
5. Default headers do not sort. Every playground demo reimplements sorting with
   a custom header slot.
6. Documented component contracts do not match the component:
   `selection-mode`, `v-model:selectedRowKeys`, `@cell-commit`, and
   `@cell-edit-commit` are documented but not implemented.
7. Server examples use `serverOptions.query`, while the public type and runtime
   require `serverOptions.fetch`.
8. The playground hides package styling defects with private theme CSS and has
   no dedicated coverage for several advertised features.
9. `AI.md` is excluded from the npm package to control package size, leaving AI
   tools without authoritative installation guidance.
10. CI verifies source behavior but does not install the packed tarball into a
    clean consumer application.
11. The repository has no npm release workflow, release scripts, or publishing
    instructions. The `.changeset/` directory is ignored and untracked, and its
    local config incorrectly marks package access as `restricted`.
12. `.gitignore` ignores `docs/` and `*.txt` globally. The planning documents
    themselves are untracked, and the planned
    `packages/playground/public/llms.txt` / `llms-full.txt` could never be
    committed or deployed without a `.gitignore` fix (verified with
    `git check-ignore`).
13. The playground's Vite aliases map only the JS entry points
    (`.`, `/unstyled`, `/minimal`) to `../vue-table/src`. Unaliased subpaths —
    including `@ioi-dev/vue-table/styles.css` — fall through to the installed
    npm dependency (`^0.2.6` in `packages/playground/package.json`). Dev mode
    therefore mixes source JavaScript with published-tarball CSS, which can
    mask or misattribute styling defects.
14. Documentation versions drift: `AI.md` is headlined `v0.2.5` while the
    package is `0.2.6`, and there is no automated doc/version consistency
    check.
15. The npm tarball `files` list contains only `dist`, `README.md`, and
    `CHANGELOG.md`. README links to `MIGRATION.md`, `API-REFERENCE.md`, or
    `AI.md` must therefore be absolute GitHub/Pages URLs, never relative
    repository paths.

## Product Goal

Version 0.3.0 will make the package dependable in a fresh Vue/Vite project and
predictable in Tailwind/shadcn projects. A consumer following the first example
must receive a readable table, sorting, pagination controls, and API behavior
that matches the documentation.

The release is judged against six outcomes:

1. **Complete on install** — the documented two-line install (component import
   plus CSS import) yields a polished, readable table in a fresh Vue/Vite app.
2. **Visible pagination** — a positive `pageSize` renders usable, accessible
   page controls (navigation, page info, page-size select) by default.
3. **Correct focus behavior** — no row appears focused or highlighted before
   the user actually interacts with the grid.
4. **Tailwind/shadcn fit** — shadcn projects style the table through their own
   CSS variables and replace interactive controls with their existing shadcn
   components via the official adapter.
5. **AI reuses the design system** — published AI guidance makes tools inspect
   the parent app and reuse its `Button`/`Input`/`Select`/pagination
   components; `/unstyled` is never the default recommendation.
6. **Truthful documentation** — every documented prop, event, slot, and server
   callback exists and behaves as described, enforced by automated
   consistency checks.

## Styling Model

The package will expose three explicit styling tiers:

1. **Default**: `Table` plus `@ioi-dev/vue-table/styles.css`. This is a complete,
   neutral, accessible table theme.
2. **shadcn**: `Table` plus `@ioi-dev/vue-table/themes/shadcn.css`. Table surfaces
   use the consumer's shadcn CSS variables. Interactive toolbar, filter, select,
   and pagination controls use the consumer's actual shadcn components through
   an official copy-paste adapter.
3. **Headless**: `@ioi-dev/vue-table/unstyled`. This is documented as an advanced
   opt-in only, never the default recommendation.

Automatic Tailwind or shadcn detection is out of scope. A library cannot safely
infer aliases, component locations, Tailwind configuration, or design tokens.
The integration must be explicit and deterministic.

**Decision (2026-06-10): CSS is delivered by explicit import, never injected by
the JS bundle.** The canonical install is two lines (`import { Table }` plus
`import '@ioi-dev/vue-table/styles.css'`). Auto-injection was considered and
rejected: chunk sharing between the `index` and `unstyled` build entries would
leak the default theme into headless consumers, the shadcn tier would need
specificity overrides to fight injected defaults, and explicit stylesheet
imports are the ecosystem pattern AI tools already generate correctly. The
"unstyled fresh install" problem is solved by completing `styles.css`
(Task 3) and documenting both lines everywhere (Tasks 4, 12), verified by the
packed-consumer fixture (Task 14).

## Component Behavior

- A positive `pageSize` enables pagination and displays native accessible
  controls by default.
- Consumers can replace the controls through a typed `pagination` slot.
- The shadcn adapter fills that slot with the project's `Button`, `Select`, and
  related components.
- Default headers sort without requiring a custom slot.
- Column sorting can be disabled per column.
- The first row is not visually focused until focus actually enters the grid.
- Selection is controllable through `v-model:selectedRowKeys`.
- Editing emits one canonical `cell-commit` event.
- Existing imperative APIs remain available.

## AI and Documentation Model

- The playground hosts `/llms.txt`, `/llms-full.txt`, and an AI integration
  guide.
- Package and repository READMEs link to the deployed GitHub Pages URLs.
- The existing `AI.md` source is versioned with the package and used as input
  when producing the hosted full AI guide, but remains outside the npm tarball.
- Guidance instructs AI tools to inspect the parent project before generating
  controls.
- If Tailwind and shadcn are present, guidance requires reuse of existing
  `Button`, `Input`, `Select`, dropdown, and pagination components.
- AI guidance must not choose `/unstyled` unless the user explicitly requests a
  fully custom/headless implementation.
- All examples use one canonical API vocabulary.

## Verification Model

Unit tests remain necessary but are not sufficient. The release gate includes:

- component behavior tests,
- CSS contract tests,
- documentation/API consistency checks,
- a packed-tarball consumer build,
- default and shadcn fixture checks,
- keyboard and accessibility checks,
- package-size thresholds,
- manual browser verification at desktop and mobile widths.

Automated checks must respect the test environment's limits: the unit suite
runs in jsdom, which performs no layout. ARIA semantics, names/roles, focus
order, and class contracts are automated (axe-core via `vitest-axe`);
anything that depends on real layout — responsive pagination wrapping,
horizontal overflow containment, sticky pinning — is verified manually in a
browser (or by an optional Playwright job), not asserted in jsdom.

## Release and Publishing Model

- Keep Changesets. It is already installed and provides version/changelog
  discipline; replacing it with manual `npm publish` would remove useful
  safeguards without simplifying the release enough to justify the change.
- Restore `.changeset/` to version control so its config and release notes are
  available to CI.
- Set Changesets access to `public`.
- Publish only from a protected `v*` Git tag after CI, packed-consumer, package
  version, and artifact checks pass.
- Prefer npm trusted publishing with GitHub Actions OIDC over a long-lived
  `NPM_TOKEN`. The release workflow receives `id-token: write` and npm is
  configured with the exact workflow filename as a trusted publisher.
  Trusted publishing requires npm CLI >= 11.5.1; use a Node version that
  bundles it (Node 24) or upgrade npm explicitly in the workflow.
- Do not commit an authentication token line to `.npmrc` for the primary flow.
  `actions/setup-node` configures the npm registry for CI. Document a
  `${NPM_TOKEN}` `.npmrc` only as a fallback for environments where OIDC cannot
  be configured.
- Verify that the GitHub Pages workflow still deploys the AI documents and
  shadcn adapter files after the playground refactor.

## Non-Goals

- Bundling shadcn as a dependency.
- Importing consumer-local `@/components/ui/*` files from package runtime code.
- Automatically rewriting Tailwind configuration.
- Replacing the existing table engine.
- Adding unrelated roadmap features such as horizontal virtualization, RTL, or
  nested column groups.
