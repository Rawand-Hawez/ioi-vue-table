# v0.3.0 Visual Issues

## 1. Column header and filter header are visually inconsistent ✅ FIXED

### What was visibly wrong

The main column-header row and the second header row containing the filters did
not have a consistent header appearance. The filter row used `--ioi-table-row-hover-bg`
instead of `--ioi-table-header-bg`, and lacked matching typography.

### Expected appearance

- In every supplied theme, the header area should have a background color that
  is slightly darker than the table body.
- The main column-header row and filter-header row should use the same
  background color.
- Both rows should use consistent typography, including font family, font size,
  font weight, and text color.
- Borders, spacing, height, and alignment should make both rows look like parts
  of one header area.
- The shared background should remain visually correct while both rows are
  sticky.
- Text, inputs, borders, and table rows must remain readable while scrolling.
- The result must work consistently in every package-supplied theme.

### How to reproduce

1. Open a table that contains both column headers and column filters.
2. Ensure the table is tall enough to scroll vertically.
3. Scroll down until the sticky header and filter row remain at the top.
4. Compare the background, typography, borders, spacing, and alignment of the
   column-header and filter-header rows.
5. Observe how the combined header area looks against the table body while it
   remains sticky.

### Acceptance criteria

- In every theme, the column-header and filter-header rows use the same
  background color.
- The shared header background is slightly darker than the table-body
  background.
- Both header rows use the same typography and compatible spacing, borders,
  height, and alignment.
- The sticky header area remains visually clean during vertical scrolling.
- There is no unintended overlap or table content bleeding through the sticky
  header area.
- The header and filter rows remain clearly separated from the table body.
- The appearance is verified with the default package styles, not only
  playground-specific CSS, and is checked in every supplied theme.

## 2. Selected rows have no visible selected state in the default theme ✅ FIXED

### What was visibly wrong

In the default table view, selecting a row did not produce a visible change.
The `--ioi-table-row-selected-bg` value (#eff6ff) was too subtle on white.
Added a left-border accent bar via `box-shadow: inset 3px 0 0` and darkened the
background to #dbeafe.

### Expected appearance

- A selected row should have an immediately recognizable visual state.
- The selected state should be visible across the full row, not only on an
  individual checkbox or cell.
- The selected-row appearance should be distinct from hover, keyboard focus,
  editing, and alternating-row styles.
- Text and controls inside the selected row must remain readable.
- Selection should remain visible when the pointer leaves the row.

### How to reproduce

1. Open a table using the default package theme with row selection enabled.
2. Select a row by clicking it or using its selection control.
3. Move the pointer away from the selected row.
4. Observe that the row has no persistent visual indication that it is
   selected.

### Acceptance criteria

- Selecting a row applies a persistent selected style across the complete row.
- Deselecting the row removes that style.
- The selected style is clearly different from hover and keyboard-focus
  styles.
- Selection remains visible after the row loses hover or keyboard focus.
- Selected-row text, links, icons, inputs, and action controls retain sufficient
  contrast.
- The behavior is verified with single-row and multi-row selection.
- The style comes from the distributed default package CSS and does not depend
  on playground-specific overrides.

## 3. CSV Export demo shows a redundant second pagination row ✅ FIXED

### What was visibly wrong

The CSV Export demo rendered a custom `.pagination-bar` div below the table
while the built-in `Table` pagination was also active. Removed the custom
pagination bar and enabled `:show-pagination="true"` with `:page-size-options`.

### Expected appearance

- The table should have one pagination area.
- Page navigation and the rows-per-page control should be presented together
  when both are needed.
- The CSV Export demo should not add a separate pagination or rows-per-page row
  below the table's primary pagination controls.
- The table footer should remain compact and visually consistent with the other
  demos.

### How to reproduce

1. Open the CSV Export demo page.
2. Scroll to the bottom of the table.
3. Observe the primary pagination controls.
4. Observe the additional row below them containing another rows-per-page
   control.

### Acceptance criteria

- The redundant second row below the main pagination area is removed.
- The CSV Export table displays only one pagination control area.
- If rows-per-page selection is retained, it appears within the primary
  pagination area.
- Pagination behavior and CSV export behavior continue to work after the
  duplicate UI is removed.
- The CSV Export footer matches the pagination structure used by the other
  playground demos.

## 4. Buttons are oversized, inconsistent, or unstyled across the playground ✅ FIXED

### What was visibly wrong

The 4 new demo pages (Pagination, Selection, Server Data, Shadcn) used
handwritten inline styles and browser-default controls instead of the shared
`.btn`, `.btn-secondary`, `.btn-ghost`, `.segment`, `.seg-btn`, `.toolbar`,
`.ctrl-group`, `.ctrl-label`, `.ctrl-input` system from `main.css`. All demos
have been rewritten to use the shared playground conventions.

### Expected appearance and behavior

- Playground controls should use one consistent UI design system.
- This requirement applies to every playground page, including demo headers,
  toolbars, forms, table actions, pagination, dialogs, benchmark controls, and
  code-example actions.
- Buttons with similar importance should have consistent height, padding,
  typography, border radius, and focus treatment.
- Primary, secondary, ghost, destructive, and segmented variants may differ in
  emphasis, but they should still look like members of the same component
  family.
- Table-theme switching must affect only the demonstrated table theme. It must
  not restyle the playground navigation, demo toolbars, forms, or action
  buttons.
- Loading or selecting the Bootstrap table theme must not permanently change
  controls on other themes or demo pages.
- Control sizing should remain compact and appropriate for a table playground.

### How to reproduce

1. Open each playground demo page.
2. Compare its primary, secondary, ghost, and segmented actions.
3. Note buttons that are oversized, appear unstyled, or do not match adjacent
   controls.
4. Select the Bootstrap table theme.
5. Switch back to Default or Tailwind.
6. Observe that globally named `.btn` controls retain Bootstrap-influenced
   sizing and appearance.

### Acceptance criteria

- The playground uses a single shared button/control implementation, preferably
  its existing Tailwind-based design system or reusable shadcn components.
- Every demo page is migrated to that shared implementation; resolving only the
  screenshot examples is not sufficient.
- Generic class names that collide with Bootstrap, such as an unscoped `.btn`,
  are removed or isolated.
- Bootstrap styling is scoped to the Bootstrap table preview or is fully
  unloaded when that theme is no longer active.
- `Capture Snapshot`, `Clear Selection`, and other demo actions use the same
  sizing and typography system as adjacent controls.
- `Auto-size All Columns` and `Auto-size Status Only` are clearly recognizable
  as related buttons, use the same dimensions, and differ only by their
  intended action hierarchy.
- The Virtual Scroll actions use the same control height, typography, spacing,
  border treatment, and responsive behavior.
- Switching repeatedly between Default, Tailwind, Bootstrap, and Minimal does
  not alter playground-level controls.
- No playground button falls back to browser-default styling.
- No ordinary playground action uses an unnecessarily large control size.
- Disabled, hover, active, focus-visible, and loading states are consistent and
  accessible.
- Button and form-control appearance is verified on every demo page at desktop,
  tablet, and mobile widths.

## 5. Virtual Scroll demo exceeds the available screen width ✅ FIXED

### What was visibly wrong

The Virtual Scroll demo toolbar could extend beyond the right edge of the
screen because `.demo-header` and `.controls` had no `max-width` or overflow
constraints. Added `max-width: 100%` and `overflow: hidden` to the demo
container, header, and controls. The table wrapper also got `overflow: hidden`
to prevent column overflow from expanding the page.

### Expected appearance and behavior

- The complete Virtual Scroll toolbar should remain inside the visible content
  area.
- The status chip, jump-to-row form, `Scroll`, `Run Benchmark`, and `Clear Log`
  controls should wrap or reorganize at narrower widths.
- No control should be clipped by the right edge of the page.
- The playground page itself should not require horizontal scrolling.
- Horizontal overflow from the table's many columns should remain inside the
  table viewport.
- The page should remain usable with both expanded and collapsed navigation.

### How to reproduce

1. Open the Virtual Scroll demo.
2. Use a browser width where all toolbar controls cannot fit on one line.
3. Observe that the toolbar extends beyond the right edge of the content area.
4. Observe that the `Clear Log` action is clipped or hidden.
5. Compare the page-level overflow with the table's own horizontal scrolling.

### Acceptance criteria

- The Virtual Scroll page never exceeds the available viewport width.
- All toolbar controls remain visible and reachable without scrolling the
  entire page horizontally.
- The toolbar wraps into clean, intentional rows when space is limited.
- The jump-to-row label, input, and submit action remain grouped together
  without forcing other controls off-screen.
- Only the table viewport scrolls horizontally when its columns exceed the
  available width.
- The table's horizontal scrollbar is visible and usable without clipping the
  surrounding page.
- The layout is verified at desktop, tablet, and mobile widths, with the
  playground navigation both expanded and collapsed.
